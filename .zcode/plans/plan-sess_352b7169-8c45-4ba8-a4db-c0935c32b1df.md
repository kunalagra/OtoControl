# Nothing/CMF driver for OtoControl (full parity with ear-web)

**Scope decision (confirmed):** Soundcore Liberty is BLE-only — no WebSerial support is possible, so it is dropped from this pass. This plan adds a Nothing/CMF driver only.

## Source of protocol truth
[radiance-project/ear-web](https://github.com/radiance-project/ear-web) — WebSerial over Bluetooth SPP:
- Service UUID for `requestPort` filters: `aeac4a03-dff5-498f-843a-34487cf133eb`, **9600 baud** (existing drivers use 115200).
- Framing: header `55 60 01 <cmdLE16> <len> <seq>` + payload + CRC-16 Modbus (poly `0xA001`, init `0xFFFF`, appended low-byte-first). No auth/handshake; on connect, poll status commands ~100 ms apart.
- Command IDs: reads ~`0xBFFF–0xC0xx` (battery `0xC007`, firmware `0xC042`, gestures `0xC018`, in-ear detection `0xC01E`, custom EQ resp `0x4044`, battery notification `0xE001`), writes `0xF000+` (ANC level payload `[0x01,0x05,0x00]`, custom EQ = ~51-byte blob with big-endian float32 band gains).
- Devices identified by model code (B171 Nothing Ear, B162 Ear (a), B163 CMF Buds Pro, B172 Buds Pro 2, B155 Ear (2), B174 Ear (open), B168 CMF Buds, etc.), each with a per-model feature table in `control.js` + per-model files (`cleffa.js`, `corsola.js`, …).

## Changes

### 1. Core seams (small, surgical)
- `src/core/brand.ts`: add `'nothing'` to `Brand` (update the pinned-value tests in `transport.test.ts` / `profiles.test.ts`).
- `src/core/transport.ts`:
  - Add `NOTHING_SPP_UUID`; new `KNOWN_SERVICES` entry `{ uuid, brand: 'nothing', protocol: 'nothing-v1' }` (extend `ProtocolGeneration`).
  - `SerialTransport.open(port, handlers, opts?: { baudRate?: number })`, default 115200 — the Nothing driver injects its own `TransportOpener` that opens at 9600 via `DriverDeps.openTransport`, so no signature changes ripple to Sony/Sennheiser.
- `src/core/profiles.ts`: `DeviceProfile` entries for the ~10 Nothing/CMF models (model regex on the model code) + `IMPLEMENTED['nothing']` feature list.
- `src/core/driver.ts`: register `NOTHING_DRIVER` in `DRIVERS`, extend `DriverId`, re-export.
- `src/core/manager.ts`: the documented hand-written part — extend the `ActiveDevice` union and the `active` getter branch (`#nothing` concrete handle). `manager.test.ts` wiring test will catch misses.
- `ui/sections/registry.ts`: icons for any new section ids; `ui/device/artwork.ts` + a placeholder asset under `public/devices/nothing/`.

### 2. New driver: `src/drivers/nothing/` (modeled on `src/drivers/sony/`)
- `frame.ts` — packet encoder + streaming `Decoder` (sync byte, header parse, CRC-16 Modbus validate), with unit tests using byte vectors taken from ear-web.
- `client.ts` — request/response over `Transport` (rolling sequence id wrapping at 250, command-id matching, timeouts, `abort(reason)` for the session hook), notification dispatch (e.g. `0xE001` battery).
- `commands.ts` — command tables and payload encode/decode: battery, firmware, ANC mode/level (+adaptive, personalized ANC `0xC020`), EQ presets + custom 8-band float32 (BE) + advanced EQ, in-ear detection, low latency (`0xC041`), gestures (`0xC018`, 4-byte records), find-my-earbuds, ear-tip fit test trigger, bass enhance.
- `models.ts` — model-code table (B1xx → name, codename, feature flags, SKU variants), firmware-version gating for adaptive ANC as in ear-web.
- `device.ts` — `NothingDevice` + `NothingState` built on `DeviceSession<NothingClient>` + `StateStore`; `adoptPort`/`disconnect`/`refresh`/`subscribe`/snapshot persistence. Model identification: derive from device-info/firmware responses where the protocol exposes it; otherwise fall back to a generic full-feature profile flagged "model unknown" — refined once you test on hardware.
- `sections/` — `NothingNoise.tsx` (ANC/transparency/adaptive), `NothingSound.tsx` (EQ presets, custom 8-band editor, bass enhance, low latency), `NothingSystem.tsx` (battery buds+case, firmware, in-ear detection, gestures, find-my-earbuds, ear-tip fit test), gated per model via `driver.sections(state)`.
- `driver.ts` — `NOTHING_DRIVER` with `as const satisfies DeviceDriver<NothingDevice, NothingState>`.

### 3. Tests
- CRC/framing round-trips with ear-web-derived vectors; battery/firmware/EQ payload decoders; driver-services ↔ `KNOWN_SERVICES` two-way check (existing `driver.test.ts` auto-covers the new entry); manager wiring test; device-orchestration tests against the fake transport like `sonyDevice.test.ts`.

## Known risks
- The SPP UUID ear-web filters on is unusual (FastPair-like rather than the standard SPP UUID). If the Chrome picker doesn't list your buds with it, fallback is an unfiltered `requestPort` + identification from port info — I'll verify against ear-web's behavior during implementation.
- Feature-level byte formats for some models (advanced EQ, personalized ANC) are only documented in ear-web's per-model JS; where ambiguous I'll port them 1:1 and mark them hardware-test-pending since you own a real device but I can't run against one.
- No Nothing hardware in dev — you'll be the integration tester; expect a short iteration loop after first connect.
